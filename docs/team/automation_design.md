# Автоматические проверки репозитория (GitHub Actions): проект

> **СТАТУС: ПРОЕКТ (не включён).** Файлы `.github/workflows/` и скрипты проверок не созданы. Включение — после решения команды (см. `docs/team/README.md`, уровень 3–4). Связано с `docs/team/collaboration.md`, `docs/team/naming_and_formats.md`, `docs/team/communication.md`.

Цель: ловить ошибки до merge — испорченный реестр, данные в git, неверные имена, утечки секретов. Проверки не заменяют ревью человека.

## 1. Что проверяем

| № | Проверка | Что ловит | Когда падает |
|---|---|---|---|
| C1 | Схема `config/sources.yaml` | пропущенные поля, неверный `status`, дубликаты `id` | любое нарушение |
| C2 | Правило 2026 | `enabled: true` без `data_2026: available` | любой такой источник |
| C3 | Данные не в git | файлы в `data/raw/`, `data/processed/` кроме `README.md` | любой такой файл |
| C4 | Имена образцов | `data/samples/*` не по шаблону | имя не совпадает |
| C5 | Образцы: размер и формат | >200 строк, >1 МБ, не UTF-8, разделитель не `;` | любое нарушение |
| C6 | Манифест `data/MANIFEST.csv` | неверный заголовок, sha256 не 64 hex, неизвестный `status` | любое нарушение |
| C7 | Секреты | токены, ключи, пароли, `.env` в diff | любое совпадение |
| C8 | Абсолютные пути | `C:\`, `D:\`, `/Users/` в документах и коде | любое совпадение |
| C9 | Относительные ссылки в `.md` | битые ссылки на файлы репозитория | ссылка не существует |
| C10 | Согласованность сводок | числа в `PROGRESS.md` и `brief.md` не совпадают с реестром | маркер не совпадает с `sources.yaml` |

Внешние URL в C9 не проверяются: они нестабильны и могут блокировать автоматические запросы.

## 2. Правила и регулярные выражения

**C1 — поля реестра** (обязательны все): `id, name, provider, role, goal, indicators, access, format, frequency, geography, status, data_2026, enabled, notes`.
- `id`: `^[a-z][a-z0-9_]*$`, уникален.
- `status`: `to_verify | verified`.
- `data_2026`: `available | N/A | unverified`.
- `enabled`: `true | false`.

**C2:** для каждого источника: если `enabled: true`, то `data_2026: available`. Год берётся из `config/project.yaml` (`target_year`). Поле `data_2026` привязано к 2026: при смене года поле переименовывается отдельной задачей.

**C3:** в `git ls-files` нет путей `^data/raw/` и `^data/processed/` кроме `README.md`.

**C4:** `data/samples/<id>/<имя>`: имя по шаблону `^[a-z][a-z0-9_]*_sample_\d{4}(-\d{2}|-Q[1-4])?(to\d{4}(-\d{2}|-Q[1-4])?)?\.csv$`.

**C5:**
- строк данных (без заголовка) ≤200;
- размер ≤1 048 576 байт;
- декодируется как UTF-8 без BOM;
- первая строка содержит `;` и не содержит `,` как разделитель.

**C6:**
- заголовок ровно: `file,source_id,period,sha256,size_bytes,downloaded_on,origin_url,member_id,status,notes`;
- `sha256`: `^[0-9a-f]{64}$`;
- `status`: `active | superseded | rejected`;
- `downloaded_on`: `^\d{4}-\d{2}-\d{2}$`.

**C7:** шаблоны для diff (только добавленные строки): `ghp_[A-Za-z0-9]{36}`, `github_pat_`, `AKIA[0-9A-Z]{16}`, `-----BEGIN .* PRIVATE KEY-----`, `(?i)(password|passwd|api[_-]?key|token)\s*[:=]\s*\S+`. Для полноты предпочтительно готовый сканер (gitleaks) — см. п. 5.

**C8:** `[A-Za-z]:\\` и `/Users/` в `*.md`, `*.py`, `*.yaml`, кроме `docs/team/` (там могут быть примеры команд).

**C10 — согласованность сводок.** В `PROGRESS.md` и `docs/stage1/brief.md` сводка реестра помечена скрытым комментарием:
```
<!-- registry-summary: total=15 available=1 enabled=1 na=2 unverified=12 -->
```
Скрипт вычисляет те же числа из `config/sources.yaml`:
- `total` — число блоков источников;
- `available` — `data_2026: available`;
- `enabled` — `enabled: true`;
- `na` — `data_2026: N/A`;
- `unverified` — `data_2026: unverified`.

Любой маркер, где хотя бы одно число не совпадает, — нарушение. Документ без маркера в списке сводок — тоже нарушение (маркер обязателен в этих двух файлах). Текст вокруг маркера свободный; числа в тексте должны совпадать с маркером (проверяется вручную при ревью).

## 3. Реализация (план)

- Один скрипт `tools/check_repo.py` (Python, только стандартная библиотека + `pyyaml`, уже в `requirements.txt`). Каждая проверка — функция, возвращает список нарушений `файл:строка: сообщение`.
- Запуск локально: `python tools/check_repo.py` — тот же результат, что в CI. Команда одна для всех ОС.
- Скрипт не читает `data/raw/` (его там может не быть, и это не нужно).
- Сообщения понятные для новичка: что нарушено, в каком файле, как исправить.

### Workflow (черновик, НЕ создан)
```yaml
# .github/workflows/checks.yml — черновик
name: checks
on:
  pull_request:
permissions:
  contents: read            # только чтение, без записи и без секретов
jobs:
  checks:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@<commit-sha>   # закрепить SHA, не тег
      - uses: actions/setup-python@<commit-sha>
        with:
          python-version: "3.13"
      - run: pip install pyyaml
      - run: python tools/check_repo.py
```

Ключевые решения:
- Триггер `pull_request`, а не `pull_request_target`: PR из форков не получают секретов и не запускают чужой код с правами записи.
- `permissions: contents: read` — проверки ничего не пишут.
- Действия закрепляются по полному SHA коммита: тег можно переназначить, SHA — нет.
- Без секретов: проверки работают без токенов.

## 4. Защита `main` (после включения)
- Статус-проверка `checks` обязательна для merge (Settings → Branches → Require status checks).
- Прямой push в `main` запрещён (см. `docs/team/collaboration.md`).
- Администратор репозитория не обходит проверку без записи в `PROGRESS.md` (причина).

## 5. Внешние инструменты (по решению)
- **gitleaks** для C7: готовое правило-набор, меньше ложных срабатываний. Подключается как действие с закреплённым SHA.
- **markdown-link-check** для C9: опционально; внешние ссылки отключить.

Каждый внешний инструмент — отдельное решение команды: это зависимость с доступом к репозиторию.

## 6. Ложные срабатывания
- Исключения — только в явном файле `tools/check_exceptions.yaml` с причиной и датой; без исключений «на глаз».
- Пример: документ с примером токена — исключение с пометкой `example`.
- Исключения проходят ревью как любой код.

## 7. Что не автоматизируем
- Качество и смысл данных (правильный ли ряд, верна ли интерпретация) — проверяет человек (см. процедуру проверки в `communication.md`, п. 6).
- Доступность внешних сайтов и актуальность ссылок — регулярная проверка вручную.
- Ответы участникам — не автоматические (см. `communication.md`).

## 8. Порядок внедрения
1. Согласовать с командой список проверок (п. 1) и исключения.
2. Написать `tools/check_repo.py` и запустить локально на текущем репозитории. Исправить найденное (например, абсолютные пути, если останутся).
3. Добавить тесты для скрипта (`tests/test_check_repo.py`): на заведомо плохих примерах каждая проверка должна падать.
4. Включить workflow и правило защиты `main` — только после шагов 2–3.
5. Записать решение в `PROGRESS.md`.

## 9. Открытые вопросы
1. Нужен ли gitleaks, или достаточно собственных шаблонов (C7)?
2. Репозиторий приватный или публичный? Для публичного стандартные раннеры GitHub Actions бесплатны без лимита минут; для приватного — минуты входят в тариф аккаунта (проверить актуальные условия на github.com перед включением).
3. Кто владеет правилами проверок и исключениями (координатор)?
