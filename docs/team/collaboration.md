# Совместная работа в команде

> **СТАТУС: ЧАСТИЧНО ПРИМЕНЯЕТСЯ.** Действуют разделы 2, 6, 8 для одного координатора: PR в `main`, защита `main` (Ruleset `protect-main`), чек-лист PR. Командные роли и распределение источников (разделы 1, 3, 7 и часть 2) — отключены до решения команды. См. `docs/team/README.md`.

Цель: исключить потерю и перезапись данных, повтор работы и конфликты в git.
Репозиторий: `origin` (GitHub). Основная ветка: `main`. Формат имён и данных — `docs/team/naming_and_formats.md`.

## 1. Роли
| Роль | Что делает |
|---|---|
| Координатор | ведёт `PROGRESS.md`, назначает источники, принимает PR в `main` |
| Владелец источника | проверяет один источник из `config/sources.yaml`, ведёт его строку в `data/MANIFEST.csv` |
| Ревьюер | проверяет PR другого участника (не свой). Пока один участник: ревью PR выполняет отдельный проход автоматического ревью (агент с чистым контекстом), блокирующие замечания — в комментариях PR |

Каждый участник — свой идентификатор `M1`, `M2`, … (не полные имена в репозитории). Идентификатор — в `git config user.name` и в колонке `member_id`.

## 2. Ветки и защита `main`
- `main` защищена: прямой push запрещён (проверено: GH013); изменения — через Pull Request.
- Ветка работы: сейчас `feature/<тема>` или `docs/<тема>` от актуального `main`; командный формат `stage<N>/<member_id>-<тема>` — после включения команды.
- Одобрение не требуется (0 approvals): автор не может одобрить свой PR. Обязательные условия merge: статус `checks` зелёный и все разговоры закрыты.
- Перед PR: локальные тесты и `python tools/check_repo.py` без ошибок (см. шаблон PR).
- Merge — squash; сообщение проверяется в диалоге merge: русский текст, без строк `Co-authored-by`.
- Не использовать `git push --force` в `main`. Свою ветку — только `--force-with-lease`, и только до merge.
- После merge: ветка удаляется локально и в origin; `main` синхронизируется `git merge --ff-only origin/main`.
- Не удалять чужие ветки.

Настройка защиты (выполнена, Settings → Rules → Rulesets, `protect-main`, Active, target `main`): restrict deletions, block force pushes, require PR (0 approvals), require status check `checks`, require conversation resolution; bypass list пуст.
Проверка: прямой `git push origin main` отклоняется с `GH013`.
Для публичного репозитория: проверить, что в нём нет данных из источников с ограничениями (см. раздел 9).

## 3. Работа по источникам (без дублирования)
1. Перед работой — issue на GitHub с id источника (например `rosstat_orc`) и именем владельца.
2. Один источник — один владелец одновременно. Занятый источник не брать.
3. Результат — строка в `data/MANIFEST.csv` и обновлённый `config/sources.yaml` (поля `data_2026`, `enabled`, `status`) в PR.
4. Закрыть issue после merge.

## 4. Данные: что где лежит
| Что | Где | В git? | Кто меняет |
|---|---|---|---|
| Исходные файлы (XLSX, PDF, HTML, JSON, SAV) | общая папка команды (облако) `data/raw/<source_id>/` | **нет** | только скачавший, один раз |
| Манифест исходных файлов (имя, sha256, дата, источник) | `data/MANIFEST.csv` | да | владелец источника через PR |
| Образцы для ревью (усечённые, ≤200 строк, ≤1 МБ) | `data/samples/<source_id>/` | да | владелец через PR |
| Обработанные таблицы | `data/processed/` | нет | только скрипты, не вручную |
| Справочники | `data/reference/` | да | через PR, с описанием в README |

Облачная папка — общая копия структуры `data/raw/`; в ней те же имена, что в манифесте.

## 5. Защита данных от порчи и перезаписи
- Исходный файл — **только для чтения** после загрузки (ПКМ → Свойства → «Только чтение» или `chmod a-w`).
- Никогда не сохранять поверх исходного файла. Для правок — копия в `data/processed/` или в рабочей папке с другим именем.
- Новая загрузка — новое имя с версией `_v2` (см. naming). Старую версию не удалять без записи в манифесте (`status: superseded`).
- Excel: не открывать исходник двойным кликом и не нажимать «Сохранить». Excel создаёт lock-файлы `~$имя.xlsx` — они не коммитятся (`.gitignore`).
- Не редактировать CSV в Блокноте с сохранением (риск смены кодировки и разделителей); использовать код или Excel «Импорт текста» с UTF-8 и `;`.
- Проверка целостности: sha256 в манифесте должен совпадать с файлом у всех участников (`certutil -hashfile <файл> SHA256` в Windows; `sha256sum <файл>` в macOS/Linux).
- Резервная копия: облачная папка + локальная копия клона. Раз в неделю координатор архивирует `data/` в ZIP с датой.

## 6. Git: безопасность
- `.gitattributes` задаёт LF в репозитории и `binary` для XLSX/PDF/SAV/DTA — бинарные файлы не портятся при merge.
- Не коммитить: ключи API, `.env`, личные данные (контакты исполнителей данных), `data/raw/`, `.venv/`.
- Перед коммитом: `git status` и `git diff --stat`. Коммитить явно названные файлы (`git add <путь>`), не `git add .`.
- Коммит: одна логическая тема; сообщение с префиксом этапа: `stage1: добавлен образец ИПЦ 2026-01…09`.
- Если случайно закоммичены данные: не force-push; координатор удаляет файл коммитом, и владелец пересоздаёт из манифеста.

## 7. Конфликты и общие файлы
- `PROGRESS.md` — один владелец на обновление за раз: правит только координатор или владелец текущего этапа. Остальные — свои строки в issue.
- Дорожная карта и статусы источников — только через PR, не параллельными правками одной строки.
- Конфликт при merge: решать в своей ветке (`git merge main`), не в `main`. Если непонятно — спросить владельца файла.

## 8. Чек-лист PR
Шаблон PR (`.github/pull_request_template.md`) заполняется полностью; ниже — дополнительные пункты по данным.
- [ ] Ветка: `feature/<тема>`, `docs/<тема>` или `stage<N>/<member_id>-<тема>` (командный формат)
- [ ] Нет файлов из `data/raw/` и больших бинарников вне `data/samples/`
- [ ] Новые файлы названы по `naming_and_formats.md`
- [ ] Строка в `data/MANIFEST.csv` добавлена (для каждого нового исходного файла)
- [ ] `config/sources.yaml` обновлён (`data_2026`, `enabled`, `status`), если затронут источник
- [ ] Образцы ≤200 строк, ≤1 МБ, UTF-8, разделитель `;`
- [ ] Нет персональных данных и ключей
- [ ] `PROGRESS.md` обновлён, если изменён статус этапа

## 9. Открытые решения (для команды)
1. Облачное хранилище для `data/raw/` (Google Drive / Яндекс Диск / OneDrive) — выбрать одно.
2. Репозиторий приватный или публичный (см. раздел 2).
3. Политика образцов: коммит усечённых образцов (принято) или только ссылки на облако.
