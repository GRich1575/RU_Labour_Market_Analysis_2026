# Вопросы для решения команды

Документ для координатора: что нужно решить, с пояснениями для участников без опыта работы с git и облачными сервисами.

Статус: открыто. Решения фиксировать здесь (дата, выбор) и в `PROGRESS.md`.

---

## Термины

- **Репозиторий** — папка проекта на GitHub вместе с историей всех изменений.
- **Ветка** — отдельная копия работы, в которой можно менять файлы, не трогая основную версию.
- **`main`** — основная ветка, та версия проекта, которую считаем рабочей.
- **Merge (слияние)** — перенос изменений из одной ветки в другую.
- **Pull Request (PR)** — запрос на слияние; другие участники просматривают и одобряют изменения до попадания в `main`.
- **Force-push** — принудительная перезапись истории на GitHub. Может стереть чужую работу, поэтому его запрещают.
- **Манифест** — список всех исходных файлов с контрольными суммами (sha256). По нему видно, что файл не испорчен и не подменён.

## 1. Видимость репозитория: приватный или публичный?

- **Что это:** кто может увидеть код и файлы. Публичный — видит весь интернет. Приватный — только приглашённые участники.
- **Почему важно:** в проекте есть заметки об источниках данных. Если данные с ограничениями или есть контакты исполнителей, публичный репозиторий может их раскрыть.
- **Варианты:** приватный (рекомендуется) или публичный.
- **Если не решить:** остаётся текущая настройка. Проверить её: GitHub → Settings → General.

## 2. Облачное хранилище для исходных данных (`data/raw/`)

- **Что это:** место, где лежат большие файлы данных, которые не попадают в git (их слишком много, и они могут содержать чувствительную информацию).
- **Варианты:** Google Drive, OneDrive, Яндекс Диск и др.
- **Рекомендация:** не использовать Яндекс Диск и другие сервисы, которые команда не может проверить как надёжные. Утечка данных и взлом аккаунта опаснее, чем неудобство. Выбрать один проверенный сервис и записать решение в `docs/team/`.
- **Учесть:** если в данных есть персональные данные, проверить требования закона 152-ФЗ о хранении данных граждан РФ до выбора сервиса.
- **Если не решить:** этап 1 не закрыть, потому что нет места для исходных файлов.

## 3. Образцы данных: коммитить или только ссылки?

- **Что это:** образец — маленький фрагмент данных (до 200 строк), который можно положить в репозиторий, чтобы другие видели формат.
- **Варианты:** (а) класть усечённые образцы в репозиторий — принято сейчас; (б) держать только ссылки на облако.
- **Рекомендация:** вариант (а), но только без персональных данных и с проверкой, что в образце нет ключей и контактов.
- **Если не решить:** действует текущая практика (вариант а).

## 4. Кто утверждает изменения в `main`?

- **Что это:** кто имеет право добавлять изменения в основную версию.
- **Варианты:** (а) один координатор сливает всё сам; (б) любой предлагает изменения через PR, а координатор или ревьюер их одобряет.
- **Рекомендация:** вариант (б), даже если участник один. Привычка защитит проект при появлении новых людей.
- **Если не решить:** координатор решает единолично, как сейчас.

## 5. Защита `main` на GitHub

- **Что это:** настройки, которые запрещают прямую запись в `main` и стирание истории.
- **Что включить:** «Require a pull request before merging» (1 одобрение), «Do not allow force pushes», «Do not allow deletions». Настраивает владелец репозитория: Settings → Branches.
- **Рекомендация:** включить. После этого скрипт `--to-main` перестанет работать напрямую (см. пункт 4).
- **Если не решить:** защиты нет, и любой с доступом может перезаписать `main`.

## 6. Кто знает git?

- **Что это:** способность самостоятельно решать конфликты при слиянии.
- **Варианты:** (а) есть человек, который может вести ветки и слияния; (б) такого человека нет.
- **Рекомендация:** если нет, работать по уровням 1–2 (имена, форматы, манифест) и не включать ветки и PR, пока не появится опытный участник.
- **Если не решить:** выбор уровня командной политики откладывается.

## 7. Кто отвечает за `main` и данные?

- **Что это:** назначить людей: кто сливает изменения, кто ведёт облачную копию и манифест.
- **Рекомендация:** назначить одного ответственного за `main` и одного за данные, даже если это один человек. Записать имена в `docs/team/README.md`.
- **Если не решить:** ответственность не определена, и при ошибке никто не отвечает.

## 8. Мессенджер для команды

- **Что это:** чат для вопросов и координации.
- **Варианты:** Telegram, WhatsApp или без группы.
- **Правила (черновик):** в чат — только усечённые образцы без персональных данных и ключей; исходные данные не загружать; решения переносить в `PROGRESS.md` или issue.
- **Если не решить:** общение идёт через GitHub issues или напрямую с координатором.

## 9. Командная политика: включать или нет?

- **Что это:** набор правил (`docs/team/`), по которым работает команда. Сейчас отключена.
- **Варианты:** (а) включить сразу; (б) включать по частям: уровень 1 (имена и форматы), уровень 2 (манифест), уровень 3 (ветки и PR), уровень 4 (защита `main`).
- **Рекомендация:** вариант (б). Включать уровень только тогда, когда команда готова его выполнять.
- **Если не решить:** политика остаётся отключённой.
